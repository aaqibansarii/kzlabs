# Insecure Direct Object Reference (IDOR) Leading to Unauthorized Access to Other Patients' Lab Results

## Vulnerability Type

Insecure Direct Object Reference (IDOR)

## Summary

The application allows authenticated users to access lab results belonging to other patients by modifying the value of the `id` parameter in the request.

An attacker can enumerate valid lab result identifiers and retrieve sensitive medical information associated with other patients without proper authorization checks.

## Vulnerable Endpoint

```http
https://kzlabs.in/703.php?action=lab_result&id=3
```

### Vulnerable Parameter

```http
id
```

## Steps to Reproduce

1. Log in to the application.
2. Navigate to the **Lab Results** section.
3. Open any lab result and intercept the request using Burp Suite.
4. Observe the request:

```http
GET /703.php?action=lab_result&id=3 HTTP/1.1
Host: kzlabs.in
```

5. Modify the value of the `id` parameter to another valid lab result identifier:

```http
GET /703.php?action=lab_result&id=8 HTTP/1.1
Host: kzlabs.in
```

6. Forward the request.
7. Observe that the application returns lab results belonging to another patient.

## Proof of Concept

The application discloses another patient's laboratory information after modifying the lab result identifier from `3` to `8`.

## Impact

* Unauthorized access to other patients' medical information
* Exposure of sensitive healthcare records
* Disclosure of laboratory test results
* Exposure of doctor notes and medical details
* Violation of patient privacy

## Recommendations for Fix

* Implement proper server-side authorization checks.
* Verify ownership of lab results before returning data.
* Enforce object-level access control for all medical record endpoints.
* Use unpredictable identifiers instead of sequential numeric IDs.
* Deny access to resources that do not belong to the authenticated user.
